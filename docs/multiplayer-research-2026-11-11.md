# 两个 Mod 的多人战役适配调查

研究日期：2026-11-11。源码基线：迁都 0.1.1、招募刷新 0.2.4。本次仅研究；没有移除生产代码的联机保护、构建联机发布包或更新工坊。Steam 保持主动离线，没有进入多人房间。

## 结论与实施顺序

迁都适合作为第一阶段：它调用原版战役接口，命令参数简单，没有候选创建和原生删除链。招募刷新有可研究的联机路线，但必须增加全端能力检查、界面释放屏障、确定性候选计划和结果比对。**不能只删 `is_multiplayer()`，也不能让房主单独调用原生删除后假定游戏会复制结果。**

建议先交付两个不同账号、不同机器的迁都联机验证，再做刷新实验。首期限制为普通双人单人类派系控制的超凡帝国战役；同时回合、辅助派系、重连和更多玩家必须各自验收，不能用双人轮流操作的结果代替。是否能稳定支持刷新，取决于原生清理及随机生成的双端实测，不预先承诺。

| Mod | 已有基础 | 必改部分 | 尚待实机证明 |
|---|---|---|---|
| 迁都 | 已使用广播请求；所有权、围城、旧首都和迁后读回检查 | 从事件派系解析请求；拆分本地 UI 权限与共享模型权限；派系请求序号和串行执行；只向发起者反馈 | 两端首都及后续贸易/收入表现一致、保存重载、同时请求排序 |
| 招募刷新 | 按人物 ID 排序的替换计划；精确引擎身份；本机原生池校验；保存履历、未知结果锁 | 上述共性修改，加全端依赖/布局握手、界面释放屏障、确定性补员模板和模型元数据解析、分阶段读回 | 随机人物及 CQI 一致、自然过回合、战斗往返、失败/重连不会继续破坏状态 |

## 来源与事实边界

主要证据是本机已安装游戏的 `data/data_script.pack`。调查时 EXE SHA256 仍为 `d2a8a58288bf8bd86768f21ff6be036cebb1916f9c312999c60afc1abe13789f`（此前验收的 9.0.5）。这说明本机基线，没有证明在线服务此时提供的最新游戏版本。

从原版脚本确认：

- `wh3_dlc23_labour_move.lua` 的 `TransferLabourActionFunctionality` 监听 `UITrigger`，用 `cm:model():faction_for_command_queue_index(context:faction_cqi())` 取得请求派系。`wh2_dlc14_malus_sanity.lua` 也使用同一路径。
- `lib_campaign_manager.lua` 的 `progress_on_all_clients_ui_triggered(trigger_name, callback)` 注册回调并广播本地派系就绪；启动时安装的监听收集派系回报，参考 `get_active_human_factions()` 的数量推进。注释明确用于把各端异步 UI 完成转换为同步推进。
- 该原版屏障按派系计数；接收处未逐一验证发送者属于预期成员集，并按处理时的活动派系数量判断。不能把它当成通用认证协议、固定成员证明或可直接应对退出/重连的事务屏障。无本地派系时其实现直接调用回调，需排除观察者/autorun 场景。
- `ScriptEventNewCharacterEnteredRecruitmentPool` 是原版经理对模型事件的本地转发，启动阶段还会排队到 first tick；它不是 Mod 自己实现的网络广播。应验证各端基础模型事件和履历一致，不能因名称就认为它自动同步所有 Lua 状态。

引擎导出文档的可浏览镜像描述了 [TriggerCampaignScriptEvent](https://chadvandy.github.io/tw_modding_resources/WH3/campaign/campaignui.html)：一个客户端发出的请求触发所有客户端的 `UITrigger`。这是文档镜像；本次同时检查上述已安装原版调用点，没有仅凭镜像推断网络时序。

依赖作者的[原始 README](https://github.com/PKozdra/memreader_plus#multiplayer)明确指出：本机指针、指针顺序和本地 UI 数据不能用于共享模型决策；模型修改必须由所有端作出相同改变。因此，“指针地址不同，所以原生调用绝不可能联机”是错误结论。每端根据相同语义人物 ID 重新定位自己的指针才是候选方案，仍须证明清理函数没有未同步的副作用。README 不是本项目已经通过联机的证据。

## 共用协议设计

1. **UI 只发送意图。** 选择目标、确认框、提示和关闭面板可以是本地行为；完整目标必须进入广播参数。模型执行不得读取鼠标、选中页、前台状态或本地 UI 缓存。
2. **全端解析同一请求派系。** 接收端以事件 `faction_cqi` 查模型派系，不再要求它等于自己的本地派系，也不把自己的 `get_local_faction_name()` 填进请求。UI 权限另行验证“这是我的派系”；模型权限验证“该事件指向有效人类派系、目标归属、允许操作阶段及没有待战”。事件中的 CQI 是协议路由信息，不能宣称为不可伪造的玩家身份；需要明确可信客户端的威胁模型。
3. **分开派系请求编号与执行队列。** 建议身份为协议版本、会话 epoch、Mod、发起派系、派系递增请求号、回合、动作、目标和前置状态。两 Mod 名字空间独立。派系各自去重，所有改变候选及随机数的操作再进入一个全局串行队列，避免随机流交错。同一时间不同玩家读到相同全局号并不应使其中一人被误判为重复。
4. **确定性状态。** 模型权限接收显式派系参数；缓存也不能因只有某端点过 UI 才成立。排序和选择按 CQI/数据库 key，禁止按指针、无序 `pairs` 或本地时间。序号必须是有界整数；游戏 Lua 单精度下需处理超过精确整数范围的情况。
5. **预检与提交区分。** 各端交换版本、模式、前置状态和能力报告，所有预期成员一致才进入提交。前置数据不一致时先禁用并诊断，不能任由一端拒绝、一端执行。不要把一个短 hash 当成完整一致性证明，数据应规范化且有长度界限。
6. **本地展示，统一结果。** 模型结果带发起派系和请求 ID；其他玩家的请求不得清除本地待提交请求，也不得弹出成功提示或重开对方招募页。错误和锁定也必须通过共享状态处理。
7. **存档迁移。** 新 schema 保存每派系请求号及结果；旧单人存档迁移须保留履历和已有 UNKNOWN/PARTIAL 锁，不能重置不明操作。运行中的网络就绪票不能在重连后复用，必须新 epoch 和新握手。不要保存原生指针。

### 序列、超时和退出

第一阶段可利用原版全端就绪屏障作实验，但必须冻结预期参与派系集合、校验每张票的发送者/请求/阶段、去重，并在成员变化时中止未提交请求、重新握手。广播事件相对其他模型命令的顺序以及屏障回调的两端模型时机仍要实测。不能以“都等 0.5 秒”代替同步。

本地墙钟超时只能触发广播取消提议或本地提示；不得让一端自行跳过成员、解锁模型状态或继续提交。已经提交后失联不承诺自动恢复；保留诊断并要求从操作前存档重开。

## 离线诊断与本地模型审阅

本次用 Lua 5.1 加载实际两个 Mod 入口，给两端不同本地派系 CQI（11、22），向两端送入同一 CQI 11 请求。入口调用计数分别为 `[1, 0]`：远端被现有本地派系过滤丢弃。其余引擎对象由 mock 提供，结果是源码诊断，**不是两台游戏的网络验证**。

实际迁都业务模块的两个派系请求都携带全局序号 1 时，第一条成功、第二条被判 `duplicate_or_invalid_sequence`。这是共享序号下的并发请求冲突演示，不代表单独这个冲突就必然造成不同步。

实际招募业务模块对相同两个候选倒序枚举，`fingerprint` 相同，但 `plan.seed.male` 分别为 `true`、`false`。因此补到 3 人时必须按稳定 ID 选模板，且将性别、职业、保护资格等实际影响决策的数据纳入语义比对。不能只扩大现在那个不包含这些字段的指纹便假定没有其他不一致源。

两项真实本地模型审阅并发执行，峰值 2，均 HTTP 200、SSE 完整、stop；输出没有满足要求的 `markdown` 字段，未作为完整候选采用。审阅中两者都把本机原生指针误判成“绝对不能联机”，还提出了与候选刷新无关的迁都接口，已拒绝。仅保留经主执行者核查的 UI/模型分离、顺序和界面状态风险分析；没有修改生产代码或把模型回答当作实机结论。

## 验收与发布门槛

- 两个独立 Lua 状态消费同一事件流：不同本地派系/界面、交错请求、重复包、旧回合、过长包、未知版本、不同 epoch、成员退出、读档恢复。比较模型操作轨迹和保存状态；这只提供离线确定性证据。
- 至少两个独立 Steam 账号、两台独立机器、相同游戏构建和相同 Mod/依赖包，在真实战役里双向操作。必要的联网联机测试是例外在线场景，先排除账号占用，完成后各自恢复主动离线；不能用同一账号顶下另一端。
- 迁都：双方各迁都、双方近同时提交、连续过回合、保存重载、战斗往返、玩家掉线。双方首都/归属/建筑/省会属性及状态一致，无重复执行、异常弹窗或 OOS。
- 刷新：双方可见不同招募页/外交页、普通及受保护人物、1→3/2→3/大池保持、反复刷新、新人物招募、下一回合自然补员。逐步比对人物 CQI、子类型、性别、姓名 key、特性、履历和操作后池成员；验证随机生成后的后续战役也一致。
- 人为制造版本/依赖/原生签名不匹配、单端校验拒绝和预提交退出，证明不生成、不删除且不消耗随机数。提交后单端原生异常属于不可回滚失败，不以自动重试或“其他端都成功”当作通过。

建议实施包：A 共用请求身份与双端离线测试；B 迁都联机实验；C 刷新全端静默/能力/状态协议；D 刷新原生双机实验及故障注入。各阶段独立验收，不在 B 通过时同时宣称招募刷新也已联机可用。
