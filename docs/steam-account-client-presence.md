# Authenticated client presence before publication

When public Steam presence is rate limited, `workshop.py --mod … --client-presence receipt.json` accepts a separately labeled receipt from a trusted background query of the current account's authenticated Steam client. This is neither a user statement nor public-profile evidence. The observer must qualify the local Steam process, its owned CEF target and `currentUserSteamID`; query the current account's persona and live CM connection without focusing or capturing Steam windows. Do not manufacture timestamps, reset the persona update age or substitute cached offline preferences.

`confirmed_idle_client_persona` requires the expected owner, exact source label, schema 1, online mode, authenticated and initialized connection/persona flags, persona 1–6, app 0, game ID `"0"`, and an empty game name. The server persona update must be at most 5 seconds old, and the UTC observation at most 30 seconds old. Missing, busy, stale, disconnected or incorrectly typed fields reject before `SteamAPI_Init`; supplied invalid evidence does not fall back to another source. The returned status is `CLIENT_PERSONA_IDLE`, retaining its source and connection fields. If both client evidence and a user confirmation are supplied, publication rejects the ambiguity.

The CLI does not obtain the receipt itself. Its caller is responsible for the trusted observation and for promptly restoring intentional Steam offline mode when the necessary online operation completes or terminates. No game should be started merely to obtain account evidence. Refresh evidence before a subsequent SDK session, since an earlier publishing session can temporarily appear as the account's active app.

Run SDK publishing in a child process and restore offline from a separate controller after that child exits. In the 0.2.4 release, `SteamAPI_Shutdown` left the Python publisher registered with Steam until process exit; offline requests during that lifetime did not produce intentional-offline readback. A new request after exit succeeded, followed by a normal-client restart and native offline proof. A mode-change acknowledgement must never be treated as successful restoration.
