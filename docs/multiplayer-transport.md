# 两个 Mod 的实验性联机传输

2026-11-11：用户授权实现，但只做单机实机验收；联机只做离线模拟。候选版本为迁都 0.2.0、招募刷新 0.3.0，尚未发布。历史研究见 [调查](multiplayer-research-2026-11-11.md)。

## 实现合同

`tools/lua/multiplayer.lua` 构建为两个包内相同的 `script/xatw3_multiplayer.lua`，在同一战役中共享一条串行总线。构建同时生成传输源码 SHA-256 和各 Mod 内容 SHA-256 模块；每端预检将实际加载的传输标识、包内容标识和模型状态一起比对。不同语言的包也会得到不同内容标识，所有参与者应安装完全相同的包及依赖。迁都仍无原生扩展依赖。

UI 提交权限属于本机派系，模型执行权限则属于事件中 CQI 解析出的请求派系。旧单机事件通道在联机模式拒绝执行，只有共享协议完成后才能调用模型逻辑。全端分别调用相同的游戏接口；不传指针，不由房主单端改模型。

阶段为 `request → ready → arm → results`。冻结并排序当前 2–8 个人类派系；请求包含存档 epoch、Mod、派系和该 Mod/派系的递增 nonce。所有端先比对版本、前置状态和执行计划，再次预检、收到最后一张一致 arm 票后各自执行，最后比较结果及模型读回。两个 Mod 同时提交按广播到达次序处理，后到者统一拒绝 busy；业务序号只在实际执行时取共享状态的当前值。只有请求发起派系收到 UI 结果。

刷新额外在所有端关闭人物面板，关闭过程中只做 UI 操作和只读检查。等待用本地回调；模型修改只能发生在同步事件处理阶段。等待期间重新打开人物面板会被关闭。就绪票覆盖具体候选的保护状态、履历、性别、姓名、背景及稳定 ID，模板按 ID 选择。支持类型检查显式使用请求派系，不依赖本机 UI 类型缓存。商队/车队和特殊训练仍不支持。

单机实测发现 `UITrigger` 将 1254 字节的请求截断到 255 字节，导致新完整指纹被误判为 stale；补充长度探针发送 240/256/257 字节，实际收到 240/255/255 字节。修正后每条联机事件最多 240 字节，分片每片携带至多 90 原始字节；逻辑消息上限 65536 字节，每端最多暂存 32 组未完成分片。epoch、长度、片数及发送派系均校验，完整消息组装后再检查请求身份，缺片时该端不执行。超限消息停止提交或投否决票。240 是本项目保留余量的限制，不承诺其他游戏构建相同。

单机继续使用本机直接通道，但完整冻结请求留在本机 UI 实例中；事件仅携带一次性引用、序号和目标。接收端必须匹配本机派系 CQI、版本、操作、序号、回合、目标与引用，消费一次后才执行冻结请求。这样大候选池的完整校验不会被事件截断，也不会把重发/过期引用误作新操作。完整请求不写入存档、不跨网络使用；面板关闭等待和直接刷新体验保持。

## 失败与恢复

- 重复票、旧 epoch、非成员和重放请求忽略；任何能力/前置状态不一致均在修改前统一拒绝。
- 本地计时器不能擅自提交、自动重试或解锁。缺少 Mod、丢票或断线可能持续等待；协议提供广播取消入口 `runtime.multiplayer.cancel()`，当前没有额外取消按钮。应从操作前存档重新开始，不能手动清空锁后继续未验证的局。
- 总线在执行前保存 pending 日志，带未完成日志的读档锁定；不恢复或重放原生操作。成员变化、结果不一致、UNKNOWN/PARTIAL 全端停止后续操作。
- 最后一次本地检查及原生调用仍可能只在某一端失败。结果比对只能发现并停止，不能回滚其他端已完成的创建/删除/迁都。客户端彻底崩溃时也不保证其结果票送达。
- 协议依赖游戏向各端可靠、有序地广播同步事件；它不实现网络重传。如果最终 arm 事件在部分端永久丢失，其他已收齐的端仍可能执行，不能把分片组装测试当作任意丢包下的原子提交保证。
- 面板关闭、广播顺序、人物 CQI/随机数消耗、保存重载与自然回合的一致性仍需真正多人局验证。离线模拟通过不代表这些游戏内性质已获证明。

## 验证边界

`tests/test_multiplayer.py` 用独立 Lua 5.1 实例和一个有序广播日志，覆盖全端恰好一次、慢端屏障、负票、快照差异、并发、缺 Mod、取消、成员变化、分片、重放、异常锁定，以及真实迁都运行模块的远端执行和本地反馈。它没有连接多人游戏。专属回归另覆盖刷新指纹、稳定性别模板和请求派系元数据。

单机实机结果和包哈希分别保存在各 Mod 的 `docs/multiplayer-implementation.json`。联机实机状态必须保持 `NOT_RUN_USER_REQUEST`；本次未更新工坊。

最终候选已分别通过 Windows x64 / 9.0.5 的单机回归：迁都实际改变首都且保持目标城属性及旧招募状态；刷新验证牧首 5→5、波耶 1→3、保护人物保留、正常招募和原生按钮避让。证据见[迁都](../mods/move_capital/docs/multiplayer-implementation.json)与[招募](../mods/recruitment_refresh/docs/multiplayer-implementation.json)。共用测试 90 项（其中传输模拟 13 项）、迁都专属 49 项、招募专属 72 项通过。这里只证明所测单机范围，不扩大为联机、全种族或其他 Mod 兼容验收。

游戏已退出，测试包/存档/脚本和生成的依赖 DLL 已清理，原偏好已恢复；Steam 主动离线的最终后台读回见[收尾回执](multiplayer-implementation-cleanup.json)。本地模型候选的传输、截断及拒绝记录见[执行账本](local-model-multiplayer-implementation-20261111.json)，没有将不完整候选拼接为生产实现。
