## 请求构造

从配置读取 `base_url`、`model`、`defaults` 与 `prompting.system_template`。当前配置连接 `http://192.168.1.11:8080/v1`，模型别名为 `qwen38-coder`，无需密钥；连接失败时检查路由、代理和服务，不自动改用旧地址。仅在排查连接时读取模型列表，不为每个任务增加探测前置。

发送 `POST /chat/completions`，保留配置默认值，设置适合任务的有限 `max_tokens`、`stream=true` 和 `stream_options.include_usage=true`。三条消息顺序如下：

1. `system`：逐字使用配置的固定系统模板。
2. `user`：按确定顺序提供当前合同、相关生产者和消费者、目标源码；源码变化时正常更新。
3. `user`：真实任务、实际诊断、明确输出格式和验收标准。

无工具模型需要实际文件内容，只有路径不足以提供上下文。不要生成占位 `request.json`，也不要把已经写好的目标实现塞进请求让模型复述。请求文件使用 UTF-8，发送前重新读取并核对最终任务字段；Windows 默认 PowerShell 管道可能把脚本内中文改成问号，本次已实际遇到该问题。可使用 UTF-8 脚本文件生成请求，避免通过不保真管道传递中文源码或任务文字。

## 并行与结果验证

输入齐备的独立任务直接并行派发，准备、审阅及必要验证与其他 HTTP 请求重叠。存在足够真实待办与服务余量时，按指南以 12–16 个实际在途请求为初始运营目标，结合错误、等待和时延调整；少量任务不为达到数字而制造调用。共享编译读窗只限制受影响的源码写入或编测，不暂停其他独立 HTTP。不同候选的输出目录和源码写权保持互斥。

HTTP 200 之后仍须检查完整 SSE 结束标志、`finish_reason`、JSON 输出合同与实际内容。`length` 或半截返回不采用、不与下一轮拼接；输出预算不足时调整范围或预算，重新发送完整请求。瞬时传输故障按配置的最多 6 次尝试及退避、抖动处理，永久请求错误先修正；重试只针对模型 HTTP，不能重放游戏动作。

记录 headers 延迟、首个非空有效 content delta 的 TTFT、总耗时及服务实际返回的 tokens。缓存字段缺失时保留未知；客户端 POST 区间不等于服务端推理并发。候选通过格式检查后再审阅、编测，分别记录原样采用、主执行者修改和拒绝，不能把传输成功当成实现正确。
