# 9.0.5 更新排查与本机验收

用户反馈普通刷新提示“操作未完成”，商路刷新后招募崩溃；具体商路页面及报错原文暂不明确。官方 9.0.5 于 2026-11-03 发布。排查开始时本机仍是 9.0.4.0 / Steam build 25961564，不能据此宣称新版本可用。

## 已确认的实现缺口及保护

- 0.2.2 的原生函数签名和对象偏移只在 9.0.4 验证过。函数签名匹配不证明另一构建的对象布局相同。候选 0.2.3 在扫描函数或读取对象前，先用 memreader Plus 的真实 `base` 和读取 API 比较 PE 时间戳、SizeOfImage 原始字节；未知身份停用原生路径。原始字节避免游戏单精度 Lua 数字丢失大整数精度。9.0.5 的调用位置静态比对及两个普通类型的实机只读对象检查通过后，加入该精确构建；实际刷新交易继续单独验收。
- 原版脚本明确存在 `wh3_main_cth_lord_caravan_master` 和 `wh3_cp1_cth_sawai_caravan` 等特殊入口。原来的自动生成元数据规则可能放行它们，且先检查缓存。现在 caravan/convoy 类型在缓存、元数据发现、生成、业务候选保护及原生对象定位前均被拒绝。未知的其他特殊机制仍不宣称兼容。
- 不清除结果不明的存档锁，不自动重试已经可能部分执行的操作。

这些是可复现的防护缺口，不是对反馈崩溃堆栈的最终归因。目前本机无此次用户崩溃原件。

## 本地模型与验证

执行机器 `pc-20260924rtuf-f11af23c08`；按配置使用本地 `qwen38-coder`。两项尚未完成的独立分析实际并发 POST，均 HTTP 200、完整 SSE、finish_reason stop。输入包括完整合同及当前原生桥、runtime、logic、UI 和测试。原始请求、流和用量保存在 `D:/workspace/.codex-wh3-runtime/update-20261104/models/`。

原生构建识别候选猜测不存在的版本 API，未采用；特殊类型候选混淆职业名称与人物子类型，代码未直接采用。主执行者采用“构建身份验证”和“特殊类型在缓存前拒绝”的设计方向，使用已核实 API 实现，并保留普通类型的现有元数据发现。两个候选没有被计作实机证据。

离线回归覆盖未知/畸形 PE 身份不得扫描或调用原生函数、特殊类型缓存不得绕过校验、不得进入生成或对象解引用。最终 9.0.5 构建身份、接口差异、普通刷新及迁都实机结论后续记录；本候选尚未发布。

最终候选 `0.2.3`、45561 字节，SHA256 `2b643bce2a34344897749bc15175ec3b8c6733d5712314624276086382e7a583` 已通过 73 项共用测试和 60 项专属测试，并在 9.0.5 离线实机通过牧首刷新（5→5，替换 3）、波耶刷新（3→3，替换 3）、受保护候选保留及新领主正常招募（金钱 6250→5500，军队数增加）。图标与原版招募、载入人物、省份切换控件无重叠且处于面板内。真实 runtime 的特殊类型缓存无法绕过支持检查，生成入口拒绝 caravan/convoy，序号和金钱未变化。

原始玩家普通报错未在此干净基线复现；没有用户商路页面的复现，也没有宣称商路可刷新。特殊招募明确禁用。完整证据见 [compatibility-9.0.5.json](compatibility-9.0.5.json) 和 [native-9.0.5.log](native-9.0.5.log)。

## 9.0.5 实机隔离结果

- 已实际安装 Steam build `26403568` / EXE `9.0.5.0`，SHA256 `d2a8a58288bf8bd86768f21ff6be036cebb1916f9c312999c60afc1abe13789f`，PE 身份原始字节 `0ba0e26a00a0530e`。所有普通验收使用新的 Steam 主动离线回执。
- EXPIRY、PURGE 完整签名各唯一命中；调用偏移与参数准备没有变化。只读桥对波耶 3 个候选全部通过定位，对牧首 5 个候选中 4 个通过、1 个受保护人物拒绝。测试桥的 `remove` 强制抛错，未执行删除。
- 新增防护初稿使用的 `string.find(..., 1, true)` 在该实机会话中会导致后续 Lua 字符串函数返回异常。逐个原版人物 getter 检查正常；只加载依赖时，首次候选池查询和字符串运算也正常。直接执行 plain-find 后，`string.sub('abcdef', 1, 3)` 返回数字 `3`；换成不含模式元字符的 `match` 后，全部只读定位和字符串完整性检查通过。该问题属于未发布候选自身，不能解释用户在 0.2.2 上的原始反馈。离线测试环境现在拒绝 plain-find 路径，防止重新引入。
- 一次受影响的诊断会话在之后点击原版城市时崩溃，日志定位到原版 `garrison_residence` 的空指针访问；这是本次测试原件，不是用户商路崩溃堆栈。没有把该会话计为刷新成功或商路复现。
- 第三项本地模型请求用于分析接口异常，完整 SSE / HTTP 200 / stop。候选错误声称 locale guard 会修改 `string.sub`，与源码不符，因而拒绝其因果结论；只保留逐步检查完整性的建议。三个请求累计数不等于并发数，实际峰值仍为前两项的 2。
- 迁都 0.1.1 在 9.0.5 已独立实机通过，详见其自己的兼容报告；不混用为本 Mod 的刷新验收。
