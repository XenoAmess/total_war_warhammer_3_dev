# 招募刷新的多人战役适配

后续实现：未发布候选 0.3.0 已接入实验协议，见[实现合同](../../../docs/multiplayer-transport.md)。下文为实现前的历史调查；本次不做联机实机验收。

当前 0.2.4 保持单人限制。原生候选删除存在联机研究路线，但暂未证明可用，也没有移除保护。

## 现有风险

- 入口和 `runtime.can_act` 绑定本机派系，远端不执行请求；`logic.execute` 调用 `adapter.supported(request.target)` 未传请求派系，动态类型发现又回落本机派系。`observe_entry` 已传派系，人物创建/招募监听没有传，必须逐处核查。
- `runtime.supported` 的 UI 访问和模型事件共用 `subtypes` 缓存。只有一端点击某类型就能改变其缓存；共享权限必须基于显式目标派系和数据库，而不能把曾经点过 UI 当作资格。
- `can_remove_candidate` 读取本机招募面板可见性。若只一端关闭面板，另一端可能拒绝，同一请求发生不同模型改变。不能简单删除这个检查，它保护旧人物卡片缓存不引用已释放对象。
- 替换计划按 ID 排序、指纹按文本排序是已有基础；但补员性别模板取第一个池条目。离线诊断已证明相同指纹、不同枚举顺序会选到不同性别。指纹也未覆盖所有保护/生成参数。
- 生成会消耗引擎随机数；数量、性别、子类型和调用顺序必须每端一致。履历状态也必须从共享模型事件派生。新人物 CQI、姓名、特性一致需要双机证明。
- `native_pool.lua` 的地址和指针应各端独立定位，绝不传输或保存指针。所有端都要执行相同语义的清理；房主单端删除不是同步方案。游戏构建、依赖版本、原生签名和池布局任一端不符时，全局停止该功能。
- 单端原生异常会在部分执行后发生。现有本地 UNKNOWN/PARTIAL 锁不能自动让其余端回滚；不存在靠 Lua 补偿就能保证恢复的事务。

## 实验协议

`请求 → 全端能力/前置状态比对 → 各端关闭并保持相关面板不可重新打开 → 每端报告就绪 → 统一提交 → 各端执行并比对结果 → 解除 UI 阻挡`

各端在本地异步等待中只做 UI/只读工作，然后发出带请求 ID 的就绪票；最终模型改变由全端收到的提交阶段推进，不能由本地秒数计时器推进。冻结参与成员集，能力或状态不一致、有人掉线、预检拒绝都不得进入生成/删除。已提交后的故障只允许停止并保留诊断，不自动重试。

原版 `cm:progress_on_all_clients_ui_triggered` 可供研究界面屏障，但它只统计就绪，不代替能力与状态一致性协议，也没有足够的成员/退出语义。依赖自带的 `memreader_plus.agree` 可另外评估版本/能力协商，当前 Mod 没有调用它；不能把有该库视为已有同步，更不能依赖它同步每次候选交易。

按稳定人物 ID 选择生成模板；全端比对规范化计划、人数和保护资格；每次原生删除重取本机指针。优先实验每一创建/删除步骤后的全端语义读回，再评估是否能在不降低故障发现能力的前提下合并通信。不能跨网络等待持有会失效的人物 UI 上下文或原生槽位。若异步边界无法安全保证，可退回“只补人数”的独立实验，但该功能不等于已经实现真正刷新。

验证必须覆盖双方不同界面、反复刷新、补到三人、受保护人物、同职业不同子类型、招募、自然回合、战斗和读档。比较实际模型数据及后续随机生成，不仅看屏幕上的人数相同。商队/车队与特殊训练继续禁止。

完整来源、共用协议、超时规则和分阶段门槛见[共性调查](../../../docs/multiplayer-research-2026-11-11.md)。本次没有联机实测、没有生产代码修改或工坊更新。
