# 迁都的多人战役适配

后续实现：未发布候选 0.2.0 已接入实验协议，见[实现合同](../../../docs/multiplayer-transport.md)。下文为实现前的历史调查；本次不做联机实机验收。

当前 0.1.1 保持单人限制。本次研究认为它适合优先实现联机，但没有发布联机支持。

明确阻断点：

- `src/script/campaign/mod/xatw3_move_capital.lua` 接收 `UITrigger` 时只接受本机派系 CQI，并用本机派系名构造执行请求；远端不会执行发起者的迁都。
- 同一入口只在非联机时安装 UI；`runtime.can_act` 同时拒绝联机，并要求请求派系等于本机派系。
- 全 Mod 的 `next_sequence` 和 `locked` 不是每派系请求状态。不同派系同时读到同一个序号会冲突，必须明确全端执行排序与派系去重。
- `runtime.on_result` 无条件清除提交标记并弹窗，开启远端执行后不能照搬；反馈只能匹配本地发起派系/请求。

实现方向：继续使用已有 `CampaignUI.TriggerCampaignScriptEvent`，全端从事件 CQI 查询同一派系；将 UI 提交权限和共享模型权限拆开；所有端按同一已验证请求调用现有 `cm:change_home_region_of_faction`。目标所属、非废墟、围城、旧首都和迁后属性的检查保留。方法调用顺序相同只是可行设计，不等于已证明该接口在真实多人局稳定。

本 Mod 无需新增 memreader 依赖。至少双机验证双方分别迁都、同时请求、保存重载和后续回合后的首都与相关表现；首期不顺带承诺辅助派系和重连。

完整协议、原版来源和验收矩阵见[共性调查](../../../docs/multiplayer-research-2026-11-11.md)。本机离线入口诊断：同一事件在本地 CQI 11、22 的两个状态中执行次数 `[1, 0]`；这不是实机联机证据。
